━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FILE 1 — app/core/config.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   It reads every secret and configuration value OpsPilot needs from the
   .env file and from real environment variables, validates them, and
   makes them available as a single Python object called `settings`.

   Any part of the app that needs a config value — an API key, a cron
   schedule, a staleness threshold — imports `settings` from this file
   and accesses it like:
       settings.slack_bot_token
       settings.stale_pr_days
       settings.is_production

   The file defines what keys exist, what types they must be, which ones
   are required vs have defaults, and what the allowed values are (for
   example, app_env must be one of: development, staging, production).
   Nothing else is accepted.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Alternative A — os.environ directly in each file
   ─────────────────────────────────────────────────
   You could write os.getenv("SLACK_BOT_TOKEN") wherever you need it.
   We didn't do this because:
     - If a key is missing, you get None silently instead of a clear
       error at startup. You only find out when the code actually runs
       and crashes mid-request.
     - There's no central list of what keys the app needs. New developers
       have to grep through the entire codebase to figure it out.
     - There's no type safety. Everything from os.environ is a string.
       If stale_ticket_days is supposed to be an integer, nothing stops
       someone from putting "five" in the .env file.

   Alternative B — a plain Python config.py with hardcoded values
   ───────────────────────────────────────────────────────────────
   You could define CONFIG = {"slack_bot_token": "xoxb-..."} directly.
   We didn't do this because secrets would end up committed to git.

   Why pydantic-settings:
   ──────────────────────
   pydantic-settings does three things at once:
     - Reads from .env file AND real environment variables automatically
     - Validates and type-converts every value (string "5" becomes int 5)
     - Gives you a clear, structured error at startup if anything is
       wrong, before any requests are ever handled

   Why the _SettingsProxy lazy wrapper:
   ─────────────────────────────────────
   When Python imports a module it runs every line at the top level.
   Without the proxy, `settings = get_settings()` would run at import
   time, which would try to load .env immediately.
   In tests there is no .env file, so this would crash before a single
   test could run.
   The proxy object looks like Settings but doesn't actually call
   get_settings() until you access an attribute on it.
   Tests never access settings attributes — they instantiate Settings()
   directly with their own test values — so the proxy never fires.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Everything. This is the most critical file in the codebase.

   Specific failures by bug type:

   Bug: A required field is removed from Settings
   → Any code that accesses that field crashes with AttributeError.
   → The Slack integration can't get its token → no briefings sent.
   → The Linear integration can't authenticate → no data collected.

   Bug: A field has the wrong type (e.g. stale_pr_days is a string)
   → The Decision agent compares ticket age (int) against a string.
   → Python raises TypeError. No staleness detection works at all.

   Bug: The _SettingsProxy is removed, singleton fires at import time
   → All 11 tests fail to even collect because the import crashes.
   → CI/CD pipeline breaks. No tests can run without a real .env.

   Bug: get_settings() loses the @lru_cache decorator
   → .env file is re-read on every single access to `settings`.
   → Performance degrades. In a high-traffic scenario this adds
     meaningful latency to every request.

   Bug: The .env file parsing silently ignores unknown keys
   → This is actually intentional (extra="ignore"). If you make a typo
     in the key name in .env (e.g. SLACK_BOT_TOKN), the field will just
     use its default value or raise "required field missing" — which is
     actually the correct safe behaviour.

FILE 2 — app/core/logging.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   It sets up how every log message in OpsPilot is formatted and where
   it goes.

   It exports two things:
     configure_logging() — call once at startup. Sets up the formatter,
                           the output handler, and the log level.
     get_logger(name)    — call at the top of any file to get a logger.

   Example usage in any other file:
       from app.core.logging import get_logger
       log = get_logger(__name__)
       log.info("pr_flagged", repo="api", pr=47, days_open=5)

   In development, this prints:
       [INFO] pr_flagged  repo=api pr=47 days_open=5

   In production, this outputs a JSON line:
       {"event":"pr_flagged","repo":"api","pr":47,"days_open":5,"level":"info","timestamp":"..."}

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Alternative A — Python's built-in print()
   ──────────────────────────────────────────
   Simple, but:
     - No log levels (can't filter debug vs error)
     - No timestamps
     - No structure — you can't search logs by field value
     - Doesn't integrate with any log management tool

   Alternative B — Python's built-in logging module directly
   ──────────────────────────────────────────────────────────
   Better, but output looks like:
       2024-01-15 09:00:00,123 INFO mymodule PR #47 is stale (5 days)
   This is a plain string. If you need to find all PRs open more than
   4 days across millions of log lines, you'd have to regex-parse strings.

   Why structlog:
   ──────────────
   structlog emits key-value structured events. In production these
   become JSON, which log management tools (Datadog, Loki, Cloud
   Logging) can index and filter natively:
       "show me all events where days_open > 4 and repo = 'api'"
   This becomes a simple database-style query, not a regex hunt.

   Why the dev/production split:
   ──────────────────────────────
   JSON is unreadable to a human during local development.
   The file checks settings.is_production and switches the renderer.
   Developer sees coloured, aligned text. Production gets machine-readable
   JSON. Same code, same log calls, different output format.

   Why silence httpx/uvicorn.access:
   ───────────────────────────────────
   These libraries are very chatty. Every HTTP request logs multiple
   lines. In a scheduled app that calls Linear/Notion/GitHub APIs every
   hour, those access logs would bury the actual business events.
   We set them to WARNING-only so they only appear if something goes wrong.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: configure_logging() is never called (e.g. removed from main.py)
   → structlog is not configured. Log calls still work but output format
     is unpredictable (structlog falls back to a basic default).
   → In production you lose structured JSON — logs can't be parsed by
     your log management tool.

   Bug: The production JSON renderer is used in development
   → Every log line in your terminal is a wall of unreadable JSON.
   → Developer experience degrades. Debugging becomes painful.

   Bug: get_logger() returns a misconfigured logger
   → Log calls throughout the app either fail silently or raise
     AttributeError (e.g. log.info doesn't exist).
   → You lose all observability. When the briefing fails to send at 9am,
     you have no idea why because there are no logs.

   Bug: Log level is not respected
   → If DEBUG logs aren't filtered out in production, you leak potentially
     sensitive information (API responses, raw ticket data) to logs.
   → If INFO logs are accidentally silenced, you miss normal operational
     events and can't tell if the system is healthy.

   Bug: noisy library logging is not suppressed
   → httpx logs every request to every API. Linear/Notion/GitHub are
     polled every run. Log volume explodes. Important events are buried.
     Log storage costs increase significantly over time.

FILE 3 — app/core/constants.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   It defines all the named labels OpsPilot uses internally across the
   entire system — agent names, data source names, severity levels,
   briefing types, staleness categories, and action types.

   Instead of raw strings scattered everywhere ("urgent", "linear",
   "collector"), the rest of the codebase uses these enums:
       AgentName.COLLECTOR    instead of "collector"
       Severity.URGENT        instead of "urgent"
       DataSource.LINEAR      instead of "linear"
       ActionType.LOG_ONLY    instead of "log_only"

   Six enums are defined:
     AgentName    → COLLECTOR, ANALYST, DECISION, ACTION
     DataSource   → LINEAR, NOTION, GITHUB, SLACK
     Severity     → URGENT, WATCH, INFO
     BriefingType → DAILY_MORNING, EOD_PULSE, WEEKLY_DIGEST, ON_DEMAND
     StaleType    → TICKET, PR, NOTION_DOC
     ActionType   → SEND_SLACK_MESSAGE, CREATE_LINEAR_TICKET,
                    DRAFT_NOTION_UPDATE, LOG_ONLY

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Alternative A — raw strings everywhere
   ───────────────────────────────────────
   agent_name = "collector"
   if severity == "urgnet":  ← typo. Python doesn't catch this.
                                The condition is just always False.
                                The founder never gets urgent alerts.
                                You have no idea why.

   With enums:
   if severity == Severity.URGNET:  ← AttributeError raised immediately.
   Python tells you at the moment of the typo, not when it's causing a
   silent production bug at 9am.

   Alternative B — plain string constants (MY_CONST = "value")
   ─────────────────────────────────────────────────────────────
   You could write AGENT_COLLECTOR = "collector". This avoids typos but
   loses another benefit of enums: iteration. With an enum you can do:
       for source in DataSource:
           fetch_data(source)
   This automatically includes any new source you add to the enum later.
   With plain constants you'd have to manually maintain a list.

   Why StrEnum specifically:
   ──────────────────────────
   Regular Enum members are not equal to strings:
       Severity.URGENT == "urgent"  →  False (with plain Enum)
   This would break any code that compares an enum value to a string
   returned by an API or stored in the database.

   StrEnum makes members both enum objects AND real strings:
       Severity.URGENT == "urgent"  →  True
   So you can store "urgent" in the database and compare it directly
   to Severity.URGENT without any conversion layer.

   Why the Python 3.10 shim:
   ──────────────────────────
   StrEnum was only added to Python's standard library in version 3.11.
   This machine runs Python 3.10.6. Rather than requiring a Python
   upgrade or adding a third-party package just for this, a two-line
   class definition (class StrEnum(str, Enum)) provides identical
   behaviour. The shim is only used on Python < 3.11 — on 3.11+ it
   imports the real StrEnum from the standard library.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: An enum value is changed (e.g. "urgent" becomes "critical")
   → Any briefing message that stored "urgent" in the database no longer
     matches Severity.URGENT.
   → Historical data breaks. The analyst agent may fail to correctly
     categorise old patterns.
   → Slack messages that checked for Severity.URGENT would stop working.

   Bug: An enum member is deleted (e.g. ActionType.LOG_ONLY removed)
   → Any agent code that references ActionType.LOG_ONLY raises
     AttributeError immediately. The entire agent pipeline crashes.
   → No briefings are sent. No actions are taken. OpsPilot goes silent.

   Bug: The StrEnum shim is broken on Python 3.10
   → Enum members are no longer equal to plain strings.
   → Database comparisons fail silently (severity stored as "urgent"
     never matches Severity.URGENT because == returns False).
   → The Decision agent filters out everything — no issues are ever
     flagged. The founder sees an empty briefing every morning.

   Bug: A new data source is added to DataSource but ActionType has no
        corresponding action for it
   → The Action agent receives a source it doesn't know how to act on.
   → Depending on how the Action agent is coded, it either crashes or
     silently does nothing with that source's findings.

FILE 4 — tests/test_config.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   It automatically verifies that config.py and constants.py work
   correctly by running 11 specific checks:

     - Settings loads successfully with the minimum required fields
     - github_repos parses "a,b, c" correctly into ["a","b","c"]
     - github_repos handles an empty string by returning []
     - is_production is True when app_env="production"
     - is_development is True when app_env="development"
     - A bad app_env value like "nonsense" raises a ValidationError
     - A bad log_level like "VERBOSE" raises a ValidationError
     - All AgentName enum values are the correct strings
     - All Severity enum values are the correct strings
     - BriefingType values are correct
     - DataSource values are correct

   Run with: python -m pytest tests/test_config.py -v

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Alternative — no tests, just trust it works
   ────────────────────────────────────────────
   The risk is that a future change breaks something invisible:
     - Someone renames stale_pr_days to pr_stale_days
     - The integration code that imports stale_pr_days now gets
       AttributeError in production at 9am on a Monday
     - Tests would have caught this in 0.06 seconds during development

   Why test validation rejection (invalid app_env, invalid log_level):
   ────────────────────────────────────────────────────────────────────
   These tests verify that the guardrails actually work. Just because
   you wrote Literal["development","staging","production"] doesn't mean
   pydantic actually enforces it — the test proves it does.
   If pydantic's behaviour changes in a future version and stops
   enforcing Literal, this test fails and you know before deploying.

   Why test enum string values:
   ────────────────────────────
   If someone refactors AgentName.COLLECTOR from "collector" to
   "Collector" (capital C), any string stored in the database as
   "collector" would no longer match. The test catches this immediately.

   Why MINIMAL_ENV dict:
   ──────────────────────
   Tests need to pass real values to Settings() without a .env file.
   MINIMAL_ENV is a dictionary containing only the required fields
   with fake but valid-format values. Each test either uses it as-is or
   overrides one specific field to test a particular behaviour.
   This keeps tests isolated — each test only changes what it cares about.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Unlike the other files, a bug in the test file doesn't break the
   running application — tests are never imported by production code.
   What breaks is your confidence and safety net:

   Bug: Tests pass when they should fail
   → False confidence. You think config.py works but it doesn't.
   → You ship a broken config validation to production. Required fields
     that should be caught at startup are silently None. The app runs
     but produces wrong results — the hardest kind of bug to diagnose.

   Bug: Tests always fail even when code is correct
   → CI/CD pipeline blocks every deployment.
   → Developers stop trusting the tests. They start skipping or
     ignoring test failures. The test suite becomes worthless.

   Bug: MINIMAL_ENV is missing a required field
   → Every test that uses MINIMAL_ENV fails with ValidationError even
     when the settings code is perfectly correct.
   → Developers waste time debugging tests instead of the real code.

   Bug: Test for github_repos parsing is removed
   → Someone later changes the parsing logic and breaks it.
   → "repo-a,repo-b" now returns ["repo-a,repo-b"] (one item, not two).
   → The GitHub integration only monitors one repo instead of several.
   → PRs in other repos are never flagged. The founder never sees them.

FILE 5 — main.py  (updated during Step 1)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   It is the entry point of the entire application. Running:
       uvicorn main:app --reload
   starts the FastAPI web server using the `app` object defined here.

   During Step 1, one thing was added: a lifespan handler.
   This is a special async function that FastAPI calls:
     - BEFORE accepting any requests → startup logic runs here
     - AFTER the server shuts down   → cleanup logic runs here

   Right now the startup logic does two things:
     1. Calls configure_logging() → structured logging is set up
     2. Logs "opspilot_startup" so you can see in logs when the server
        came online

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Alternative — call configure_logging() at the top of main.py
   ─────────────────────────────────────────────────────────────
   You could just call configure_logging() as a top-level statement
   when the module is imported. The problem: imports happen before
   FastAPI's own setup. If logging is configured before settings are
   fully initialised, the log level might not be set correctly yet.
   The lifespan approach guarantees startup code runs after the app
   is fully constructed.

   Alternative — @app.on_event("startup") decorator
   ──────────────────────────────────────────────────
   This was FastAPI's old pattern. It's now deprecated. FastAPI
   recommends lifespan. Using the old pattern would generate deprecation
   warnings in every log and would need to be refactored later anyway.

   Why log "opspilot_startup":
   ───────────────────────────
   In production, when you look at logs you need to know when the server
   last restarted. If briefings stopped at 9:02am and the server
   restarted at 9:01am, that's your answer. Without a startup log entry,
   you're guessing.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: lifespan is removed, configure_logging() is never called
   → Logging falls back to structlog's unconfigured default.
   → In production: no JSON output. Log management tool sees nothing.
   → You lose all observability. When something goes wrong at 3am,
     you have no logs to diagnose it.

   Bug: app.include_router(router) is missing
   → The API has no routes. Every request returns 404.
   → The Slack webhook endpoint doesn't exist.
   → On-demand queries from Slack ("OpsPilot what's blocking X?") fail.

   Bug: The lifespan yield is removed
   → FastAPI starts but immediately considers the app "shut down".
   → No requests are ever served.
   → The server appears to be running but returns nothing.

   Bug: The prefix "/api/v1" is changed or removed
   → All API route paths change. Any client calling /api/v1/query
     now gets 404. Slack's webhook URL (stored in Slack's config)
     stops working and can't receive events without manually updating
     the Slack app settings.
