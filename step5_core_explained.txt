FILE 1 — app/scheduler/jobs.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Five things live here, grouped by concern:

   A) Three async job coroutines — one per scheduled briefing.

      morning_briefing_job()
        → Called every day at 09:00.
        → Calls run_pipeline(briefing_type=BriefingType.DAILY_MORNING).
        → Full pipeline: all sources, PR reviews enriched, LLM analysis,
          complete Slack Block Kit briefing.

      eod_pulse_job()
        → Called every day at 18:00.
        → Calls run_pipeline(briefing_type=BriefingType.EOD_PULSE).
        → Lighter run: run_pipeline auto-detects EOD_PULSE and skips
          PR review enrichment (saves ~10s of GitHub API calls).

      weekly_digest_job()
        → Called every Sunday at 18:00.
        → Calls run_pipeline(briefing_type=BriefingType.WEEKLY_DIGEST).
        → Full pipeline with LLM trend and velocity analysis.

      All three follow the same error contract:
        Non-fatal: run_pipeline already surfaces partial errors in
          state["run_errors"] and logs them internally.
        Fatal (pipeline raises): the job catches the exception, logs
          it with the full traceback, and RETURNS NORMALLY.
          The scheduler process survives. The next tick fires normally.

   B) _log_job_result(job_name, state) — private helper.
      Extracts action_result.briefing_sent and run_errors from the
      final state and emits one structured log line summarising the
      outcome. Called at the end of every successful job function.

   C) start_scheduler() — creates, configures, and starts the scheduler.

      Creates an AsyncIOScheduler instance and registers three jobs:
        morning_briefing  → CronTrigger.from_crontab(settings.daily_briefing_cron)
        eod_pulse         → CronTrigger.from_crontab(settings.eod_pulse_cron)
        weekly_digest     → CronTrigger.from_crontab(settings.weekly_digest_cron)

      Each job is registered with:
        replace_existing=True  — safe to call start_scheduler() again
        max_instances=1        — prevents overlapping runs
        misfire_grace_time=300 — tolerates up to 5-minute late fire

      Stores the scheduler in the module-level _scheduler variable,
      calls _scheduler.start(), logs the registered job IDs, and
      returns the scheduler instance.

   D) stop_scheduler() — graceful shutdown.
      If _scheduler is not None and is running, calls
      _scheduler.shutdown(wait=True). wait=True blocks until any
      currently-executing job finishes before returning.

   E) get_scheduler() — returns the current _scheduler instance or None.
      Used by API routes that need to inspect or manually trigger jobs.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why AsyncIOScheduler instead of BackgroundScheduler?
   ──────────────────────────────────────────────────────
   BackgroundScheduler runs jobs in a thread pool. Our job coroutines
   are async — awaiting run_pipeline(), which itself awaits HTTP calls,
   LLM calls, and Slack sends. Running async code inside a thread pool
   requires creating a new event loop per thread, which conflicts with
   uvicorn's existing asyncio event loop. AsyncIOScheduler dispatches
   coroutines directly on the running event loop — no threads, no new
   event loop, no conflict.

   Why CronTrigger.from_crontab(settings.daily_briefing_cron)?
   ─────────────────────────────────────────────────────────────
   The schedule lives in settings (read from .env), not hardcoded.
   The operator can change "0 9 * * *" to "30 8 * * *" (8:30 AM) via
   an environment variable and restart the server — no code change,
   no deploy. from_crontab() accepts standard 5-field cron syntax, the
   same format already stored in config.py.

   Why max_instances=1?
   ─────────────────────
   Without it, if a morning briefing run takes 45 seconds and the next
   scheduled tick fires (hypothetically, if the cron overlaps), two
   pipeline runs execute concurrently. Both post to Slack. The founder
   receives two identical morning briefings. max_instances=1 prevents
   the second run from starting until the first finishes.

   Why misfire_grace_time=300?
   ────────────────────────────
   Cloud Run with min-instances=1 prevents most cold starts, but not
   all — a deployment restart can cause a brief window where no instance
   is running. If the 9am job was supposed to fire during that window,
   APScheduler marks it as "misfired." Without a grace period, a misfired
   job is silently skipped — the founder gets no morning briefing with
   no explanation. With 300 seconds (5 minutes), if the server comes back
   up within 5 minutes of the scheduled time, the job fires anyway.

   Why do job functions catch all exceptions instead of letting them
   propagate?
   ─────────────────────────────────────────────────────────────────
   APScheduler's default behaviour on an unhandled exception in a job:
   it logs the error and continues. But our jobs are async coroutines,
   and the interaction between APScheduler's exception handling and
   asyncio is version-dependent. Catching explicitly in the job function
   is the safest, most portable approach — we control exactly what
   happens (structured log with traceback) and we're certain the
   scheduler process is never affected.

   Why store the scheduler in a module-level _scheduler variable?
   ──────────────────────────────────────────────────────────────
   The scheduler is created in start_scheduler() but needs to be
   accessible from stop_scheduler() (called later in the lifespan
   shutdown path) and get_scheduler() (called by API routes).
   A module-level variable is the simplest correct solution — the
   scheduler is a singleton anyway (one per process in Phase 1).

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: Job functions do NOT catch exceptions from run_pipeline()
   → If Gemini is down or Slack returns 500, run_pipeline() raises.
   → The uncaught exception propagates into APScheduler's internals.
   → APScheduler logs it, but depending on the version and asyncio
     interaction, the scheduler may stop processing jobs entirely.
   → The founder stops receiving all briefings until the server restarts.

   Bug: max_instances not set (or set to a high number)
   → A slow morning run (e.g. Gemini takes 40s) overlaps with the
     next tick. Two concurrent pipeline runs post two identical Slack
     briefings. Founder is confused. Trust in the tool drops.

   Bug: misfire_grace_time=0 (or not set)
   → Any job missed during a restart or deployment is silently dropped.
   → The founder notices the 9am briefing didn't arrive but has no
     way to know whether OpsPilot is broken or just skipped.

   Bug: stop_scheduler() uses wait=False
   → The server process exits while a pipeline run is still mid-execution.
   → The Slack send is interrupted. The founder may receive a truncated
     or empty briefing. The Supabase audit log entry is never written.
   → Linear ticket creation may be half-completed (ticket created but
     description not written), leaving malformed tickets in the board.

   Bug: CronTrigger uses hardcoded hour=9 instead of from_crontab
   → The operator cannot change the schedule without modifying code.
   → More critically, settings.daily_briefing_cron is ignored, so any
     timezone offset or schedule customisation in .env has no effect.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Defines the public API of the scheduler package. Six names exported:

     start_scheduler      — called once from main.py lifespan on startup
     stop_scheduler       — called once from main.py lifespan on shutdown
     get_scheduler        — called by API routes that need the instance
     morning_briefing_job — exported so tests can call jobs directly
     eod_pulse_job        — exported for the same reason
     weekly_digest_job    — exported for the same reason

   Without this file, main.py would import from the internal file:
     from app.scheduler.jobs import start_scheduler, stop_scheduler
   If jobs.py is ever split or renamed, every importer breaks.
   With __init__.py:
     from app.scheduler import start_scheduler, stop_scheduler

2. WHY DID WE MAKE IT THIS WAY?
   Same stable-public-surface pattern as integrations/, agents/, graph/.
   The scheduler package's internal file structure is an implementation
   detail. Callers (main.py, API routes, tests) depend only on the
   package-level names, not on which file they live in.

   Exporting the three job functions specifically lets test code call
   morning_briefing_job() directly without constructing a scheduler,
   which is the right way to test job logic in isolation.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: start_scheduler not exported
   → main.py's import fails. Server refuses to start.
   → ImportError is clear and immediate — easy to fix, but must be
     caught before deployment.

   Bug: stop_scheduler not exported
   → Server starts fine. Scheduler runs.
   → On shutdown, the lifespan's stop_scheduler() call fails silently
     if the import was already cached. Or raises ImportError if not.
   → If it fails silently, APScheduler keeps running in the background
     after the server "shuts down," firing jobs with no HTTP server to
     receive their results.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Two changes were made to the existing main.py:

   A) Added the scheduler import:
        from app.scheduler import start_scheduler, stop_scheduler

   B) Updated the lifespan() asynccontextmanager:

      Before (Step 4):
        @asynccontextmanager
        async def lifespan(app):
            configure_logging()
            log.info("opspilot_startup")
            yield
            log.info("opspilot_shutdown")

      After (Step 5):
        @asynccontextmanager
        async def lifespan(app):
            configure_logging()
            log.info("opspilot_startup")
            start_scheduler()        ← new: boots the scheduler
            try:
                yield
            finally:
                stop_scheduler()     ← new: shuts it down cleanly
                log.info("opspilot_shutdown")

   The try/finally wrapping the yield is critical — see below.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why call start_scheduler() inside lifespan instead of at module load?
   ──────────────────────────────────────────────────────────────────────
   If start_scheduler() ran at module import time, it would fire during
   pytest collection — before any test runs. The scheduler would start
   making real pipeline calls (or fail trying to) in the test process.
   Placing it in lifespan() means it only runs when the FastAPI app
   actually starts — not during imports or test collection.

   Why try/finally instead of bare yield?
   ────────────────────────────────────────
   This is the real bug caught during Step 5 testing.

   With bare yield:
     start_scheduler()
     yield           ← if the server body raises, execution jumps here
     stop_scheduler() ← NEVER REACHED if yield raises

   Python's asynccontextmanager only runs code after yield on normal
   exit. If an exception propagates through the yield (e.g. uvicorn
   receives SIGKILL, or an unhandled exception bubbles up), code after
   the bare yield is skipped entirely. The scheduler is never stopped.
   It continues firing jobs in a zombie state with no HTTP server.

   With try/finally:
     start_scheduler()
     try:
         yield
     finally:
         stop_scheduler()  ← ALWAYS RUNS, whether normal or exception

   The test test_lifespan_stop_called_even_if_startup_body_raises
   caught this bug by raising RuntimeError inside the async with block
   and asserting that stop_scheduler() was still called. It failed
   with the bare yield, passed after the try/finally fix.

   Why configure_logging() before start_scheduler()?
   ───────────────────────────────────────────────────
   The scheduler's startup log (scheduler_started) uses structlog.
   If the scheduler started before configure_logging(), that first log
   line would use Python's default formatter (plain text) instead of
   the structured JSON/colour format. Always configure logging first.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: start_scheduler() not called in lifespan
   → No cron jobs are registered. Server starts and serves HTTP fine.
   → The 9am briefing never fires. Founder notices at 9:05am.
   → No error anywhere — the scheduler just doesn't exist.
   → Debugging is painful: no log line, no exception, just silence.

   Bug: stop_scheduler() not called in lifespan (no finally block)
   → Normal shutdown: fine — the process exits and OS cleans up.
   → Deployment restart: Cloud Run sends SIGTERM, uvicorn starts
     graceful shutdown, lifespan cleanup runs. Without stop_scheduler(),
     APScheduler.shutdown(wait=True) is never called. If a job is
     mid-run (e.g. the 9am briefing started at 9:00:01 and SIGTERM
     came at 9:00:15), it is killed mid-execution. Incomplete briefing.
     Possible duplicate Slack posts on the next startup.

   Bug: stop_scheduler() called before yield (wrong position)
   → The scheduler is stopped before the server ever starts serving.
   → No briefings fire during the server's lifetime.
   → Same silent failure mode as "not called at all."

   Bug: configure_logging() removed from lifespan
   → All logs for the entire session use Python's default formatter.
   → In production: GCP Cloud Logging can't parse plain text as
     structured JSON. Log-based alerts and filters stop working.
     Errors become invisible in the logs dashboard.

1. WHAT DOES THIS FILE DO?
   20 unit tests, zero real API calls, zero real scheduler loops.
   run_pipeline() is patched with AsyncMock throughout.
   APScheduler's .start() and .shutdown() are patched with MagicMock.
   Organised into 4 test classes:

   TestJobFunctions (6 tests)
     → morning_briefing_job passes DAILY_MORNING to run_pipeline.
     → eod_pulse_job passes EOD_PULSE to run_pipeline.
     → weekly_digest_job passes WEEKLY_DIGEST to run_pipeline.
     → All three job functions survive a fatal exception from
       run_pipeline() without re-raising (scheduler process safety).

   TestSchedulerLifecycle (6 tests)
     → start_scheduler() registers exactly 3 jobs.
     → The 3 registered job IDs are the correct strings.
     → start_scheduler() calls scheduler.start().
     → stop_scheduler() calls scheduler.shutdown(wait=True).
     → stop_scheduler() when _scheduler is None is safe (no error).
     → get_scheduler() returns the current module-level instance.

   TestLogJobResult (4 tests)
     → Successful run (briefing_sent=True) logs without error.
     → Run with errors surfaces the first error string.
     → Missing action_result (None) handled gracefully.
     → Empty run_errors logs first_error=None safely.

   TestMainLifespan (4 tests)
     → start_scheduler() is called on server startup.
     → stop_scheduler() is called on server shutdown.
     → stop_scheduler() is called even when the server body raises
       (the test that caught the bare-yield bug).
     → main.py imports both start_scheduler and stop_scheduler.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why patch AsyncIOScheduler entirely instead of using a real one?
   ─────────────────────────────────────────────────────────────────
   A real AsyncIOScheduler needs a running asyncio event loop to attach
   to. In tests with pytest-asyncio in strict mode, the loop lifecycle
   is tightly controlled. Creating a real scheduler, starting it, then
   shutting it down in each test risks loop-already-closed errors and
   test isolation issues. A MagicMock that records .add_job() and
   .start() calls is sufficient to verify the wiring without any of
   the asyncio complexity.

   Why test job function exception handling specifically?
   ──────────────────────────────────────────────────────
   This is the most critical safety property of the scheduler layer:
   "a failed briefing must never crash the scheduler." If someone
   refactors a job function and removes the try/except, the tests
   catch it immediately. Without these tests, the regression would
   only be discovered when a Gemini outage takes down the entire
   scheduler process.

   Why test _log_job_result() separately instead of only through
   the job functions?
   ─────────────────────────────────────────────────────────────
   _log_job_result() reads action_result.briefing_sent from the state
   dict. If action_result is None (pipeline crashed before action_node
   ran), it must not raise AttributeError. Testing it in isolation with
   None, empty errors, and error strings pins down all edge cases without
   the complexity of a full job function test.

   Why does the lifespan shutdown test patch module attributes directly
   instead of using unittest.mock.patch()?
   ─────────────────────────────────────────────────────────────────────
   patch("main.stop_scheduler") only works if "main" hasn't been
   imported yet — it patches the name in the module's namespace.
   But in a test session, main is already imported by the time
   TestMainLifespan runs. Using patch() in a with block creates a
   new MagicMock and sets it on the module, but the lifespan coroutine
   was defined before the patch took effect, so it still holds a
   reference to the original function object.

   The fix: import main, save the originals, replace the module
   attributes directly, run the test, restore in a finally block.
   This is the correct pattern for testing code that has already been
   imported and whose functions reference global names at call time
   (not at definition time).

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: AsyncMock not used for run_pipeline (MagicMock used instead)
   → run_pipeline() is a coroutine — it must be awaited.
   → MagicMock is not awaitable. job functions raise TypeError:
     "object MagicMock can't be used in 'await' expression."
   → All 6 job function tests fail with a confusing error.

   Bug: TestSchedulerLifecycle does not reset _scheduler between tests
   → stop_scheduler_calls_shutdown injects a mock into _scheduler.
   → The next test (stop_when_none_is_safe) sets _scheduler = None.
   → But if they run in a different order, _scheduler from one test
     leaks into another. Our tests avoid this by injecting/restoring
     _scheduler explicitly in each test that needs it.

   Bug: The lifespan shutdown test asserts mock_stop.assert_called_once()
        INSIDE the pytest.raises() block (before the context exits)
   → The assertion runs before the finally block of lifespan executes.
   → stop_scheduler() hasn't been called yet. The assertion always fails
     even when the code is correct.
   → The assertion must be OUTSIDE (after) the pytest.raises() block.
     This is already correct in our tests — worth knowing it must stay.

  THE BUG CAUGHT BY TESTS
════════════════════════════════════════════════════════════════════════

  The bare-yield lifespan bug is worth calling out separately because
  it is a common Python mistake that has real operational consequences.

  The original lifespan (before the fix):
    start_scheduler()
    yield
    stop_scheduler()   ← skipped on exception, skipped on SIGKILL

  The fixed lifespan:
    start_scheduler()
    try:
        yield
    finally:
        stop_scheduler()   ← always runs

  In Python, asynccontextmanager does NOT guarantee post-yield code
  runs on exception unless you use try/finally. The test
  test_lifespan_stop_called_even_if_startup_body_raises raised
  RuntimeError inside the async with block and asserted that
  stop_scheduler() was called. It failed with the original code
  and passed after the fix. This is the correct way to write and
  test cleanup code in async context managers.
