━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FILE 1 — app/integrations/models.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Defines the data shapes — Pydantic models — that all four integrations
   produce and all downstream agents consume.

   Models defined:
     LinearTicket     — one Linear issue (id, title, status, assignee,
                        updated_at, days_since_update, is_unassigned...)
     PullRequest      — one GitHub PR (number, repo, author, days_open,
                        has_no_reviewer, review_decision...)
     NotionPage       — one Notion page (id, title, last_edited,
                        days_since_edit, is_stale...)
     SlackMessage     — one inbound Slack message to OpsPilot
     SlackBriefingPayload — a fully assembled briefing ready to post
     CollectorSnapshot — the combined output of one full collection run
                         (all tickets + PRs + pages + any errors)

   It also has a shared helper `_days_ago(dt)` that computes how many
   days ago a datetime was, used by all the `days_since_*` properties.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Alternative — pass raw API dicts between agents
   ───────────────────────────────────────────────
   You could have each integration return the raw JSON from the API and
   let the agents parse it. Problems:
     - Linear's JSON looks nothing like GitHub's JSON. Each agent would
       need to know the specific shape of every API it reads from.
     - If Linear changes a field name (they have before), bugs appear in
       the Analyst agent, not in the Linear client where they belong.
     - You can't test the Analyst agent without real API responses.

   Why Pydantic models specifically:
   ──────────────────────────────────
   Pydantic validates the data at the boundary (when the integration
   client creates the model). If the Linear API returns a ticket missing
   a required field, Pydantic raises a ValidationError immediately in
   linear.py — not later in the Analyst agent where the cause is unclear.

   Why computed_field for days_since_update, is_stale, etc:
   ─────────────────────────────────────────────────────────
   These are computed from the stored datetime each time they're accessed.
   This means they're always current — a ticket that was "3 days old"
   when collected but stored in the DB will correctly show "4 days old"
   the next day. No need to recalculate and re-store.

   Why CollectorSnapshot:
   ───────────────────────
   The Collector Agent runs all four integrations and needs to hand one
   clean package to the Analyst Agent via LangGraph's state.
   CollectorSnapshot is that package. It also carries an `errors` dict
   so if Notion is down, the agent logs it but still delivers Linear and
   GitHub data — partial success instead of total failure.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: LinearTicket field is renamed (e.g. updated_at → last_updated)
   → Every place that accesses ticket.updated_at raises AttributeError.
   → The Analyst agent can't compute staleness. Decision agent gets no
     stale tickets. Founder never gets warned about them.

   Bug: _days_ago returns a negative number
   → All staleness checks fail. days_since_update is -3 which is never
     >= the 5-day threshold. No tickets are ever flagged as stale.
   → OpsPilot sends empty briefings. Founder thinks everything is fine.

   Bug: CollectorSnapshot errors field is removed
   → When an integration fails (e.g. GitHub rate limit), the Collector
     has nowhere to record it. It either crashes entirely or silently
     drops the error. No one knows GitHub data is missing.

   Bug: is_stale property uses wrong comparison (< instead of >)
   → Recent pages flagged as stale, old pages ignored. Notion update
     alerts are completely wrong.

FILE 2 — app/integrations/base.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   A base class that Linear and GitHub clients inherit from. It provides:
     - An httpx.AsyncClient with base URL and auth headers pre-set
     - A _request() method that wraps every HTTP call with:
         * Automatic retry (up to 3 times) on 429 and 5xx responses
         * Exponential backoff (waits 2s, 4s, 8s between retries)
         * Respects Retry-After headers from rate limit responses
         * Structured logging of every request and response
     - _get() and _post() convenience wrappers
     - Async context manager (with async with LinearClient() as c: ...)

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Alternative — copy-paste retry logic into each client
   ──────────────────────────────────────────────────────
   Every integration hits rate limits. Linear, GitHub, and Notion all
   return 429 when you call them too fast. Without shared retry logic,
   you'd write the same try/except/sleep code 3+ times. A bug in the
   retry logic would exist in 3 places.

   Why tenacity over a manual retry loop:
   ────────────────────────────────────────
   Manual: while retries < 3: try: ... except: sleep(); retries += 1
   Problems: error-prone, doesn't handle jitter, hard to configure.
   tenacity handles exponential backoff, jitter, exception filtering,
   attempt counting, and re-raising cleanly in one decorator.

   Why httpx over requests:
   ────────────────────────
   requests is synchronous. This app is async (FastAPI + asyncio).
   Calling a synchronous HTTP library inside an async function blocks
   the entire event loop — other requests can't be processed while
   waiting for the API. httpx has a native async interface.

   Why async context manager pattern:
   ────────────────────────────────────
   httpx.AsyncClient should be reused across requests (connection
   pooling) but must be explicitly closed. The context manager guarantees
   close() is called even if an exception occurs mid-collection.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: Retry logic is removed
   → The first 429 from Linear or GitHub raises an exception immediately.
   → The entire morning briefing fails if any API hiccups.
   → Common scenario: GitHub's rate limit resets at midnight; the 9am
     run hits a brief limit. Without retry, no GitHub data in briefing.

   Bug: _client is not properly closed after use
   → httpx.AsyncClient connections leak. Over time (many scheduler runs)
     the process accumulates open connections until the OS refuses more.
   → Server becomes unreachable. Requires a restart to fix.

   Bug: Auth headers are not injected
   → Every API call returns 401 Unauthorized. No data is collected.
   → All four integrations fail silently if the error isn't logged.

   Bug: _request() swallows exceptions instead of re-raising
   → API failures return None instead of raising. Calling code gets None
     where it expects a dict and crashes later with a confusing error.

FILE 3 — app/integrations/linear.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Talks to the Linear GraphQL API and returns structured data.

   Two public methods:
     fetch_open_tickets(team_id, limit)
       → Runs a GraphQL query that fetches all issues not in "completed"
         or "cancelled" state for the team.
       → Returns a list of LinearTicket objects.

     create_ticket(title, description, team_id)
       → Runs a GraphQL mutation to create a new Linear issue.
       → Used by the Action agent when OpsPilot auto-creates tickets
         (e.g. "this Slack question has been asked 3 times, create a
         ticket for it").
       → Returns {success, id, url}.

   Internally, _graphql() handles the POST to /graphql and checks for
   the "errors" key in the response (GraphQL returns 200 even for errors).
   _parse_ticket() maps the raw node dict to a LinearTicket model.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why GraphQL and not a REST client:
   ────────────────────────────────────
   Linear only has a GraphQL API — there's no REST alternative.
   GraphQL lets us request exactly the fields we need in one round trip.
   The query fetches: id, title, status, assignee, team, dates, comments,
   labels — all in a single request.

   Why check for "errors" in the response:
   ──────────────────────────────────────────
   GraphQL always returns HTTP 200, even when the query fails. A REST
   API returns 400 or 500, which httpx catches automatically. GraphQL
   errors are in the JSON body under the "errors" key. If we didn't
   check for this, a malformed query would return silently with no data
   and no exception — the Analyst gets an empty list and doesn't know why.

   Why limit=250 default:
   ────────────────────────
   Linear's API returns max 250 nodes per query. For a 5-25 person
   startup, 250 is enough to see all open tickets. If a team has more,
   pagination would be needed (left for later).

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: The GraphQL query has a typo in a field name
   → Linear returns an error in the "errors" key. _graphql() raises
     RuntimeError. fetch_open_tickets() propagates it. Collector catches
     it and records it in CollectorSnapshot.errors["linear"]. Briefing
     is sent but says "Linear data unavailable."

   Bug: _parse_ticket() uses wrong key (e.g. "updated" instead of "updatedAt")
   → KeyError when parsing every ticket. Collector fails entirely on
     the Linear step. No ticket data in the briefing.

   Bug: create_ticket() doesn't check result["success"]
   → A failed mutation (e.g. invalid team ID) returns silently as success.
   → The Action agent thinks it created a ticket but nothing was made.
   → The founder expects a ticket to appear in Linear; it never does.

   Bug: Authorization header uses wrong format
   → Linear expects: Authorization: <api_key> (no "Bearer" prefix).
     If "Bearer" is added, all calls return 401. No ticket data collected.

FILE 4 — app/integrations/github.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Talks to the GitHub REST API and returns structured PR data.

   Two public methods:
     fetch_open_pull_requests(repos, enrich_reviews)
       → For each configured repo, fetches all open PRs (paginated).
       → Optionally calls /pulls/{n}/reviews per PR to get the review
         decision (APPROVED, CHANGES_REQUESTED, or pending).
       → Returns a flat list of PullRequest objects across all repos.
       → Per-repo errors are logged and skipped — other repos continue.

     fetch_recent_commits(repo, branch, limit)
       → Returns the last N commit messages for a branch.
       → Used by the Analyst agent to summarise "what shipped this week"
         from commit messages.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why httpx directly instead of PyGithub SDK:
   ─────────────────────────────────────────────
   PyGithub is synchronous — it would block the event loop.
   It also wraps every response in heavy objects. We only need 6-8 fields
   from a PR. Using httpx directly is lighter, async, and gives full
   control over the request/response cycle.

   Why enrich_reviews is a toggle:
   ─────────────────────────────────
   Getting review state requires one extra API call per PR. A team with
   20 open PRs across 3 repos = 20 extra calls per collection run.
   Making it optional lets us run faster collections (e.g. EOD pulse)
   with reviews disabled, and thorough morning briefings with reviews on.

   Why per-repo error isolation:
   ──────────────────────────────
   If one repo is archived or the token lacks access to it, we log the
   error and continue to the next repo. The briefing still includes all
   other repos. Without this, one bad repo would silently drop all PRs.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: Pagination loop doesn't advance the page counter
   → Infinite loop fetching the same first page of PRs forever.
   → The collection run never finishes. The briefing is never sent.

   Bug: Per-repo errors are not caught
   → A single repo returning 403 (access denied) crashes the entire
     fetch_open_pull_requests() call. No PR data in any repo.

   Bug: _parse_datetime() is not called on PR dates
   → created_at and updated_at are raw strings. days_open raises
     TypeError when it tries to subtract a string from datetime.now().

   Bug: Review enrichment always runs even when enrich_reviews=False
   → Extra API calls slow collection significantly. With 50 PRs, 50
     extra calls add ~10 seconds to every run. At GitHub's rate limits,
     it might trigger 429s, delaying the briefing further.

FILE 5 — app/integrations/notion.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Talks to the Notion API using the official notion-client SDK.

   Three public methods:
     fetch_all_pages(limit)
       → Searches the workspace for all pages the integration can access.
       → Paginates automatically using Notion's cursor system.
       → Skips archived pages.
       → Returns a list of NotionPage objects.

     fetch_stale_pages(stale_days)
       → Calls fetch_all_pages() then filters by days_since_edit.
       → Returns only pages older than the threshold.
       → Used by the Analyst agent as the stale doc detection step.

     append_to_page(page_id, text)
       → Adds a paragraph block to an existing page.
       → Used by the Action agent to draft Notion updates.
       → Returns True/False — never raises (soft failure).

   Also includes _extract_title() which handles the fact that Notion
   pages can store their title under different property keys
   ("Name", "Title", "title", "name") depending on how the page was
   created.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why the official notion-client SDK instead of raw httpx:
   ──────────────────────────────────────────────────────────
   Notion's pagination is cursor-based and the SDK handles it. Notion's
   authentication is also integrated. Writing raw httpx calls for Notion
   would require re-implementing their cursor pagination and auth — 50+
   lines of boilerplate for no benefit. The SDK is async-native.

   Why _extract_title() exists:
   ─────────────────────────────
   Notion pages don't always use "title" as the property key. A database
   page might use "Name". A template might use "Title". Without this
   function, many pages would appear as "Untitled" in the briefing even
   when they have names. The function tries common keys in order.

   Why append_to_page returns True/False instead of raising:
   ──────────────────────────────────────────────────────────
   The Action agent sends updates to many pages. If one page fails (e.g.
   the integration doesn't have write access to it), a hard crash would
   stop all subsequent updates. Soft failure lets the agent continue and
   log which pages it couldn't update.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: Pagination cursor is not passed on second page
   → Only the first 100 pages are ever fetched. For a large workspace,
     many pages are invisible to OpsPilot. Stale doc detection misses
     them. They're never flagged even if 6 months old.

   Bug: archived pages are not filtered out
   → Archived pages appear in the stale list. The briefing tells the
     founder "Q2 OKRs hasn't been updated in 400 days" about a page
     that was intentionally archived. Noise, not signal.

   Bug: append_to_page raises instead of returning False
   → Action agent crashes mid-run trying to update the first inaccessible
     page. All subsequent Notion updates (even to accessible pages) are
     skipped.

   Bug: _extract_title() returns empty string instead of fallback
   → Every page with a non-standard title key shows as "" in the briefing.
   → The founder sees alerts about unnamed pages with no idea which doc
     is being referred to.

FILE 6 — app/integrations/slack.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Handles all Slack communication — both outbound (sending) and inbound
   (receiving and verifying).

   Class: SlackClient
     send_text(text, channel, thread_ts)
       → Posts a plain text message. Used for simple alerts.
     send_briefing(payload)
       → Posts a formatted Block Kit briefing with headers, sections,
         dividers. The rich format the founder reads every morning.
     reply_in_thread(channel, thread_ts, text)
       → Replies inside a Slack thread. Used for on-demand query answers.
     parse_event(event_body)  [static]
       → Converts a raw Slack Events API payload into a SlackMessage.
       → Filters out bot messages and messages with no text.
     verify_request_signature(body, timestamp, signature, signing_secret)  [static]
       → Verifies the HMAC-SHA256 signature Slack attaches to every
         webhook. Rejects requests older than 5 minutes (replay attacks).

   Module-level Block Kit builders:
     build_header_block, build_section_block, build_divider_block,
     build_context_block, build_briefing_blocks
       → Helper functions that assemble the Slack Block Kit JSON for the
         daily briefing. The Action agent calls build_briefing_blocks()
         with categorised items to produce the final message.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why Block Kit instead of plain text:
   ──────────────────────────────────────
   Plain text Slack messages look like chat. Block Kit messages look like
   a structured report — headers are bold and large, dividers separate
   sections, context blocks appear smaller. It makes the briefing
   scannable in 90 seconds, which is the core product promise.

   Why verify_request_signature takes signing_secret as a parameter:
   ──────────────────────────────────────────────────────────────────
   Originally it read from settings directly. Problem: it's a static
   method, and testing it required mocking settings (which triggered the
   lazy proxy). Making the secret an explicit parameter turned it into a
   pure function — testable with zero mocking. This also makes it usable
   in contexts where you want to verify without touching settings.

   Why parse_event filters bot messages and empty text:
   ──────────────────────────────────────────────────────
   If OpsPilot sends a message, Slack fires an event for it. Without
   filtering bot_id, OpsPilot would receive its own messages, try to
   answer them, send another message, receive that, and loop forever.

   Why signature verification rejects requests older than 5 minutes:
   ──────────────────────────────────────────────────────────────────
   A replay attack works like this: attacker captures a valid signed
   Slack request and re-sends it later. The HMAC signature is still
   valid — but the timestamp is old. The 5-minute window ensures that
   even a perfectly signed but old request is rejected.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: verify_request_signature always returns True
   → Any HTTP request to the /webhook endpoint is treated as legitimate.
   → Attackers can send fake Slack events, triggering OpsPilot to send
     arbitrary messages or create tickets. Security breach.

   Bug: parse_event doesn't filter bot_id
   → Infinite feedback loop: OpsPilot messages itself, answers itself,
     messages again. Floods the Slack channel. Hits rate limits.

   Bug: send_briefing swallows SlackApiError without logging
   → The morning briefing fails to send but the scheduler thinks it
     succeeded. Founder sees nothing at 9am with no error anywhere.

   Bug: build_briefing_blocks adds urgent items even when list is empty
   → Briefing always shows "🔴 URGENT — Needs your attention today"
     even when there's nothing urgent. Founder loses trust in the signal.

FILE 7 — app/integrations/__init__.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Defines the public API of the integrations package. Anything listed
   in __all__ can be imported cleanly by other modules:
       from app.integrations import LinearClient, CollectorSnapshot

   Without this file, other modules would need to know the internal
   file structure:
       from app.integrations.linear import LinearClient
       from app.integrations.models import CollectorSnapshot
   If we ever rename or restructure files, every import would break.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?
   Explicit __all__ list + flat imports is the Python standard package
   pattern. It creates a stable public surface — internal file names can
   change without breaking anything outside the package. The agent code
   only depends on the public interface, not on file locations.

3. WHAT BREAKS IF THIS FILE HAS A BUG?
   Bug: A new model or client is added but not listed in __all__
   → It can still be imported from its specific file, but the clean
     from app.integrations import X form won't work. Inconsistency
     forces developers to know internal file names again.

   Bug: A circular import is introduced
   → Python refuses to load the module. The entire app fails to start.
   → Error at startup, not at runtime — easy to diagnose but must be
     fixed before the app can run.

FILE 8 — tests/test_integrations.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   29 unit tests that verify the integrations layer with zero real API
   calls. Organized into 6 test classes:

     TestLinearTicket (6 tests)
       → days_since_update, is_unassigned, is_active (started/completed/
         cancelled)

     TestPullRequest (5 tests)
       → days_open, has_no_reviewer in three states, days_since_update

     TestNotionPage (3 tests)
       → days_since_edit, is_stale above and below threshold

     TestCollectorSnapshot (4 tests)
       → has_errors True/False, empty snapshot, snapshot with data

     TestSlackSignatureVerification (3 tests)
       → Valid HMAC accepted, wrong signature rejected, stale timestamp
         rejected — all using signing_secret passed directly (no mocking)

     TestSlackEventParsing (4 tests)
       → Valid message parsed, bot messages ignored, non-message events

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why no real API calls in tests:
   ─────────────────────────────────
   Real API calls require valid tokens and network access. Tests would:
     - Fail in CI (no secrets available)
     - Be slow (each call takes 200-800ms)
     - Be flaky (rate limits, network hiccups)
     - Mutate real data (create_ticket would make real Linear tickets)

   Why test computed fields (days_open, is_stale) specifically:
   ─────────────────────────────────────────────────────────────
   These computed fields are the core of OpsPilot's logic — they answer
   "is this thing stale?" If the calculation is off by one day, tickets
   get flagged a day too early or too late. The test nails the exact
   boundary behaviour.

   Why test SlackClient.parse_event exhaustively:
   ───────────────────────────────────────────────
   The event parser is the entry point for all on-demand queries. If it
   incorrectly passes through a bot message, it causes an infinite loop
   (OpsPilot talks to itself). The test suite explicitly covers the
   bot_id filter, subtype filter, and empty text filter.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: Helper fixtures (_make_ticket, _make_pr) use wrong defaults
   → Tests pass with incorrect values. A ticket always has assignee=None
     even when testing is_unassigned=False behaviour. Test gives false
     confidence — the real logic might be broken but tests still pass.

   Bug: Signature tests pass the wrong body to verify_request_signature
   → The HMAC is computed over one body but verified against another.
   → The test always fails even when the implementation is correct.
   → Developers disable or remove the test. Signature verification goes
     untested. A future bug in it goes undetected.

   Bug: TestBlockKitBuilders doesn't test the "empty sections omitted"
        behaviour
   → Someone removes the `if urgent_items:` guard in build_briefing_blocks.
   → Every briefing now shows "URGENT" even with zero urgent items.
   → Founder sees false urgent alerts daily. Loses trust in OpsPilot.
