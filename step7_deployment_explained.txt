  OPSPILOT — STEP 7  |  Deployment & Packaging
  Dockerfile, docker-compose.yml, .dockerignore

OVERVIEW
────────
Step 7 takes the fully tested OpsPilot application and packages it into a 
standardized, production-ready container. Because we built everything with 
stateless endpoints, environment variable configs, and an integrated async 
scheduler, our deployment footprint is just a single lightweight container.

Three files were created:
  1. Dockerfile
  2. docker-compose.yml
  3. .dockerignore


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FILE 1 — Dockerfile
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   It defines the environment and steps to build the OpsPilot container.
   - Uses `python:3.10-slim` as a lightweight base.
   - Sets environment variables to optimize Python for containers (`PYTHONDONTWRITEBYTECODE=1`, `PYTHONUNBUFFERED=1`).
   - Copies `requirements.txt` and installs dependencies first.
   - Copies the rest of the application code.
   - Exposes port `8080` (standard for Cloud Run).
   - Sets the startup command to `uvicorn main:app --host 0.0.0.0 --port 8080`.

2. WHY DID WE MAKE IT THIS WAY?
   Layer caching: By copying `requirements.txt` and running `pip install` BEFORE
   copying the rest of the code, Docker caches the heavy dependency installation
   step. If you change a single line in `main.py`, the next Docker build takes 
   seconds (just copying the code layer) instead of minutes (re-downloading 
   all pip packages).

3. WHAT BREAKS IF IT HAS A BUG?
   Bug: Forgetting `--host 0.0.0.0` in the uvicorn command.
   → Uvicorn defaults to `127.0.0.1`. Inside a Docker container, `127.0.0.1` 
     only binds to the container's internal loopback interface. No outside traffic 
     can reach it. GCP Cloud Run will fail to route traffic and crash the deployment.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FILE 2 — docker-compose.yml
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   It provides a simple way to build and run OpsPilot locally with a single 
   command: `docker compose up --build`.
   - Maps host port `8080` to container port `8080`.
   - Automatically injects the `.env` file into the container.

2. WHY DID WE MAKE IT THIS WAY?
   It guarantees "it works on my machine" translates to "it works in production."
   Running the app directly via Python on your Mac/PC might hide environment 
   issues that only appear in Linux. `docker-compose` bridges that gap for local testing.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FILE 3 — .dockerignore
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   It tells Docker which files and directories to completely ignore when copying
   the context into the image during `COPY . .`.
   - Ignores `.git/`, `.env`, `__pycache__/`, `tests/`, and all `.txt` explanation files.

2. WHY DID WE MAKE IT THIS WAY?
   Security & Size. 
   - Size: We don't want to upload hundreds of MBs of local virtual environments 
     (`.venv/`) to the image registry. 
   - Security: We MUST NOT bake the `.env` file (containing real API keys) into the 
     image itself. If the image is ever pushed to a registry, anyone who pulls it 
     could extract the keys.


════════════════════════════════════════════════════════════════════════
  GCP CLOUD RUN DEPLOYMENT
════════════════════════════════════════════════════════════════════════

To push this live to Google Cloud Run:

1. Submit the build to Artifact Registry:
   gcloud builds submit --tag gcr.io/YOUR_PROJECT_ID/opspilot

2. Deploy the service:
   gcloud run deploy opspilot \
     --image gcr.io/YOUR_PROJECT_ID/opspilot \
     --platform managed \
     --region us-central1 \
     --min-instances 1 \
     --memory 512Mi \
     --set-env-vars-from-file .env \
     --allow-unauthenticated

Why --memory 512Mi?
LangGraph + Gemini calls can spike memory. Cloud Run's default 256Mi will OOM-kill your container mid-briefing. 512Mi is safe for Phase 1.

Why --min-instances 1?
Because OpsPilot handles its own scheduled cron jobs via APScheduler in the 
FastAPI lifespan, we cannot let Cloud Run scale the container down to 0 when 
idle. If it scales to 0, the 9 AM trigger will never fire. Keeping 1 instance 
alive ensures the scheduler runs on time.
