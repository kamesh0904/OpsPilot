━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FILE 1 — app/agents/models.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Defines the data shapes that flow between all four agents.
   The integrations layer (Step 2) produced raw data shapes (LinearTicket,
   PullRequest, etc). This file defines what those get transformed INTO.

   Models:
   AnalystFinding — one flagged issue (title, detail, severity, source,
     item_url, days_overdue, suggested_action).
     Has a computed finding_id (MD5 of source+item_id) for deduplication,
     and a to_slack_line() method that formats it as Slack markdown.

   AnalystReport  — everything the Analyst produced in one run:
     findings (list of AnalystFinding), shipped_items (strings of
     positive signals), patterns (LLM-generated), llm_used (bool).
     Computed urgent_count and watch_count.

   DecisionOutput — the briefing content, already formatted:
     urgent_items, watch_items, shipped_items (all Slack markdown strings),
     suggestion (one sentence), raw_findings (for Action agent).
     Computed is_empty.

   ActionResult   — what the Action agent actually did:
     briefing_sent, channel, tickets_created, notion_pages_updated, errors.
     Computed success (bool).

   AgentState     — the single object that flows through LangGraph:
     briefing_type, snapshot, report, decision, action_result, run_errors.
     Used in Step 4 (app/graph/).

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why a separate models.py instead of putting models in each agent file?
   → Each agent needs to read what the previous agent produced. If
     AnalystFinding lived in analyst.py, the decision.py file would import
     from analyst.py — coupling two agents together. Putting models in one
     neutral file means any agent can import from models.py without
     depending on another agent.

   Why finding_id is an MD5 hash (not a random UUID)?
   → Deduplication requires the same finding to produce the same ID across
     runs. A random UUID would be different every time — the Decision agent
     couldn't tell "this is the same stale PR I flagged yesterday."
     MD5(source + item_id) is always the same for the same item, so the
     Decision agent can skip it on the next run.

   Why to_slack_line() lives on AnalystFinding?
   → The Decision agent calls it when formatting for Slack. If this logic
     lived in the Decision or Action agent, you'd need to pass both the
     finding object AND know the formatting rules in two places. Keeping
     it on the model means "a finding knows how to display itself."

   Why AgentState holds Optional fields?
   → At the start of a run, only briefing_type is known. snapshot is None
     until Collector runs. report is None until Analyst runs. LangGraph
     updates state node by node — fields must be Optional so early nodes
     don't require data that doesn't exist yet.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: finding_id uses random UUID instead of deterministic hash
   → Deduplication breaks. Every finding gets a new ID on every run.
   → The Decision agent never skips anything — the founder sees the same
     stale PR flagged in every morning brief until it's fixed.

   Bug: to_slack_line() always shows "overdue" even when days_overdue=0
   → Every finding in the briefing shows "+0d overdue" next to it.
   → Looks unprofessional. Founder loses trust in the output quality.

   Bug: DecisionOutput.is_empty doesn't check shipped_items
   → A briefing with only shipped items (positive signals, no alerts)
     is treated as empty. The Action agent sends nothing. The founder
     gets no briefing at all on a good, clean day.

   Bug: AgentState fields are not Optional
   → LangGraph can't create an initial state — it requires all fields
     to be populated before the first node runs. The entire pipeline
     fails to start.

FILE 2 — app/agents/collector.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Runs all three integration clients (Linear, GitHub, Notion) at the
   same time and packs everything into a CollectorSnapshot.

   The single public method run() does this:
     1. Calls asyncio.gather() with three private fetch methods
     2. Each fetch method opens its client and calls the integration
     3. gather() waits for all three to finish (or fail)
     4. Results are checked — exceptions become entries in snapshot.errors
     5. Returns CollectorSnapshot with whatever succeeded

   The three private methods are thin wrappers:
     _fetch_linear()  → async with LinearClient() as c: return await c.fetch_open_tickets()
     _fetch_github()  → async with GitHubClient() as c: return await c.fetch_open_pull_requests()
     _fetch_notion()  → async with NotionClient() as c: return await c.fetch_all_pages()

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why asyncio.gather() instead of calling them one after another?
   → Sequential: Linear (2s) + GitHub (3s) + Notion (2s) = 7s total.
   → Parallel:   all three at once = ~3s total (slowest one wins).
   → At 9am the founder is waiting for the briefing. 4 seconds faster
     matters. At scale with more integrations it matters even more.

   Why return_exceptions=True in gather()?
   → Without this flag, if GitHub raises an exception, gather() raises
     immediately and cancels the other two tasks. Linear and Notion data
     is lost even though those calls succeeded.
   → With return_exceptions=True, the exception becomes a return value.
     We check isinstance(result, Exception) and put it in errors{}. The
     briefing still runs with partial data.

   Why are _fetch_*() private methods instead of inline lambdas?
   → Testability. Each fetch method can be patched independently:
       with patch.object(agent, "_fetch_linear", return_value=[...])
     If the logic was inline inside run(), you'd have to patch the entire
     client class, which is heavier and more coupled.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: gather() used without return_exceptions=True
   → One failing integration crashes the entire collection run.
   → At GitHub's rate limit reset (common around midnight/early morning),
     the 9am briefing fails entirely. Founder gets nothing.

   Bug: Exceptions are silently swallowed (not put into snapshot.errors)
   → Integration failures are invisible. The founder sees an empty
     briefing with no explanation. No way to know if Notion was down
     or simply has no stale pages.

   Bug: The three fetch methods are called sequentially (not in gather)
   → Collection takes 3x longer. The briefing is delayed. APScheduler
     might time out the job and the briefing never sends.

   Bug: snapshot.errors uses DataSource enum keys but code uses strings
   → snapshot.has_errors returns True correctly, but downstream code
     that checks errors["linear"] gets KeyError because the key is
     actually DataSource.LINEAR. Inconsistency causes crashes in the
     Analyst or Action agent when they inspect errors.

FILE 3 — app/agents/analyst.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Takes a CollectorSnapshot and returns an AnalystReport by running
   two stages of analysis:

   Stage 1 — Rule-based (always runs):
     _analyse_tickets(): flags Linear tickets not updated in N days
       (N = settings.stale_ticket_days, default 5).
       Unassigned + stale → URGENT. Assigned + stale → WATCH or URGENT
       depending on how far past the threshold.
     _analyse_prs(): flags GitHub PRs open N days with no reviewer
       → URGENT. PRs past threshold with reviewer → WATCH or URGENT.
       Draft PRs are always skipped.
     _analyse_notion(): flags Notion pages not edited in N days
       → WATCH. Archived pages are always skipped.
     Findings are sorted: URGENT first, then by days_overdue descending.

   Stage 2 — LLM (runs if google_api_key is set and use_llm=True):
     Builds a prompt containing all tickets, PRs, and rule-based findings.
     Sends to Gemini via langchain-google-genai.
     Asks for: cross-source patterns + one actionable suggestion.
     Response is expected as JSON: {"patterns": [...], "suggestion": "..."}
     If Gemini fails or the JSON is malformed, _parse_llm_response()
     returns ([], None) and the run continues with Stage 1 results only.

   Also builds shipped_items: recently updated open PRs and recently
   closed tickets — the positive signals for the briefing.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why two stages instead of just asking Gemini to do everything?
   → Reliability. LLM calls fail (rate limits, API outages, invalid key).
   → If the entire Analyst was one Gemini prompt, any LLM failure means
     zero findings. With rule-based as the foundation, the briefing still
     catches every clearly stale item even when Gemini is down.
   → Cost. The rule-based stage catches the obvious stuff for free. Gemini
     is only invoked for the value-add: cross-source patterns that are
     hard to express as rules.

   Why langchain-google-genai instead of calling the Gemini API directly?
   → Langchain abstracts the API call, handles async, and makes it trivial
     to swap models (change settings.gemini_model to any supported model).
   → with_structured_output() is available if we later want Pydantic
     model output directly from the LLM (Step 5 enhancement).

   Why ask for JSON in the prompt instead of free text?
   → Free text from an LLM can't be reliably split into "patterns" vs
     "suggestion." JSON enforces a parseable structure. If Gemini returns
     something that's not valid JSON, _parse_llm_response catches the
     parse error and returns empty defaults — safe failure.

   Why strip markdown code fences in _parse_llm_response?
   → Gemini often wraps JSON responses in ```json ... ``` even when you
     don't ask for it. Without the stripping logic, json.loads() fails on
     every response that includes fences.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: Stage 1 uses > instead of >= for staleness check
   → A ticket at exactly the threshold (e.g. 5 days) is never flagged.
   → The founder is promised "we'll alert you after 5 days" but the alert
     only fires at day 6. Users lose trust in the threshold setting.

   Bug: Draft PRs are not filtered out
   → Every draft PR that's been open for N days appears as URGENT in the
     briefing. Developers get notified about PRs that are intentionally
     not ready for review. Noise kills trust in the signal.

   Bug: _llm_analysis is awaited but Gemini raises synchronously
   → If the langchain call raises before the first await, the exception
     propagates out of the try/except in run() differently than expected
     on some Python versions. Safer: always wrap in try/except at the
     top of the LLM call, which we do.

   Bug: _parse_llm_response crashes instead of returning defaults
   → Any malformed Gemini response crashes the entire Analyst run.
   → Every run that touches Gemini fails. Rule-based findings are lost.
   → The founder gets nothing.

   Bug: The prompt includes all 250 Linear tickets without capping
   → A team with a large backlog sends a 50,000-token prompt to Gemini.
   → Exceeds context limit → API error. LLM stage always fails.
   → We cap at 50 tickets and 30 PRs in the prompt to prevent this.

FILE 4 — app/agents/decision.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Takes the AnalystReport and decides exactly what goes in the briefing.

   _bucket_findings(): splits findings into urgent/watch. Skips any
     finding whose finding_id is in _seen_finding_ids for this
     briefing_type (deduplication across runs).

   Capping: urgent is capped at 5 items, watch at 4.
     More than this is overwhelming — the founder would stop reading.

   _pick_suggestion(): returns the most actionable next step:
     1. Use finding.suggested_action if set (from Analyst)
     2. Auto-generate: "Address [title] — flagged for N days"
     3. None if no findings

   _build_shipped_lines(): converts AnalystReport.shipped_items and
     patterns into display strings (patterns shown as "💡 ...").

   Dedup store: _seen_finding_ids is a module-level dict.
     Keys are briefing_type strings, values are sets of finding_ids.
     After each run, the set is updated with what was shown.
     Next run: anything in the set is skipped.
     This is in-memory only — resets on server restart. Step 5 adds
     DB persistence.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why deduplicate here and not in the Analyst?
   → The Analyst's job is to find everything that is objectively stale.
   → The Decision agent's job is to decide what to bother the founder
     about. Those are separate concerns. If you put dedup in the Analyst,
     the Analyst's output no longer reflects reality — it hides findings
     based on presentation logic.

   Why cap at 5 urgent / 4 watch?
   → The product promise is "reads in 90 seconds." If you show 15 urgent
     items, the founder either ignores it or stops opening the briefing.
     A briefing that's always ignored is worse than no briefing at all.
     These caps enforce the promise.

   Why is dedup per briefing_type?
   → A stale PR flagged in the morning brief should still appear in the
     EOD pulse — the founder might have forgotten about it by 6pm.
   → If dedup was global, items seen in any run would never reappear.
     Separate sets per briefing_type means each type has independent
     memory.

   Why in-memory instead of DB now?
   → DB persistence is Step 5 (app/db/). Building it now would couple
     the agent to the database before the schema is even defined.
   → The in-memory approach is correct behaviour — it works perfectly
     within a single process uptime. Step 5 replaces it transparently.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: Dedup set is never updated after each run
   → Nothing is ever deduplicated. The same stale PR appears in every
     single briefing until it's closed. Founder sees repeated alerts
     and starts ignoring them.

   Bug: Dedup set is never cleared (grows forever)
   → After a PR is closed and re-opened (edge case) or a new item gets
     the same finding_id (hash collision, extremely rare), it's
     permanently suppressed. The founder never sees it again.

   Bug: Cap is removed or set to a very high number
   → A team with 20 stale tickets gets a wall of text in Slack.
   → Blocks don't render correctly at extreme lengths.
   → The 90-second readability promise is broken.

   Bug: _bucket_findings uses == instead of in for the seen check
   → The seen check compares a string to a set (always False for 'in').
   → Wait, that's a type error: x == {set} is always False.
   → Nothing is ever deduplicated. Same effect as the "never updated" bug.

FILE 5 — app/agents/action.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Executes the three possible actions based on DecisionOutput:

   _send_briefing(): calls build_briefing_blocks() (from slack.py) with
     the categorised items, wraps in SlackBriefingPayload, sends via
     SlackClient.send_briefing(). Also builds a plain text fallback via
     _build_fallback_text() for notification previews.

   _create_tickets() [optional, off by default]:
     For findings from GitHub or Notion (not Linear — those are already
     tickets), creates a Linear ticket titled "[OpsPilot] {finding.title}"
     with full context in the description. Max 2 tickets per run.

   _update_notion_pages() [optional, off by default]:
     Appends a warning note to each stale Notion page found in the
     findings. Note says "OpsPilot flagged this as stale on [date]."
     Max 3 pages per run.

   _build_fallback_text(): builds a plain text summary for the Slack
     notification banner (shown when Block Kit doesn't render, e.g. in
     mobile push notifications). Maps briefing_type to a human label.

   All three action methods catch exceptions per item and add to errors[]
   rather than propagating — so a failed ticket creation doesn't stop the
   Notion updates or Slack send.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why are auto_create_tickets and auto_update_notion off by default?
   → OpsPilot should never do things the founder didn't explicitly enable.
   → Creating Linear tickets automatically is high-impact and potentially
     confusing ("where did this ticket come from?"). It's opt-in.
   → Notion writes modify content the team relies on. Opt-in only.

   Why build fallback text even though we send Block Kit?
   → Slack's mobile app shows a notification banner using the text field,
     not the blocks. If text is empty, the notification says "sent a
     message" — useless. The fallback text gives the founder the gist
     of the briefing before they even open Slack.

   Why max 2 tickets / 3 Notion updates per run?
   → Auto-actions should feel like assistance, not automation gone rogue.
   → If 12 items are URGENT and the agent creates 12 tickets at once,
     the Linear board is flooded. Caps prevent runaway behaviour.

   Why use _ensure a separate async with SlackClient() inside _send_briefing?
   → The Action agent doesn't hold a long-lived client connection — it
     opens and closes one per action. This prevents connection leaks if
     one of the optional actions fails between client open and close.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: _send_briefing doesn't add to errors[] on failure
   → briefing_sent = False but no error is recorded.
   → ActionResult.success returns True (no errors) even though the
     briefing was never sent. The scheduler thinks the run succeeded.
   → The founder never receives the briefing and there's no alert.

   Bug: _build_fallback_text returns empty string
   → Slack notifications say "You have a new message" with no context.
   → Founder doesn't know if it's urgent or routine. Engagement drops.

   Bug: _create_tickets doesn't filter out Linear-source findings
   → OpsPilot creates Linear tickets about Linear tickets — a ticket
     that says "[OpsPilot] Fix login bug" gets created inside Linear
     about a ticket that is ALREADY in Linear.
   → Duplicates flood the board.

   Bug: errors list is not passed by reference into each private method
   → Actually it IS passed by reference (Python lists are mutable).
     But if someone changes to errors = [] inside a method instead of
     errors.append(), the outer list is not affected and errors are lost.

FILE 6 — app/agents/__init__.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   Exports all four agent classes and all five model classes under the
   app.agents namespace. The LangGraph graph (Step 4) imports everything
   from here:
       from app.agents import CollectorAgent, AnalystAgent, DecisionAgent, ActionAgent

2. WHY DID WE MAKE IT THIS WAY?
   Same reasoning as integrations/__init__.py: stable public surface.
   Internal file names can be reorganised without breaking imports.

3. WHAT BREAKS IF THIS FILE HAS A BUG?
   Bug: AgentState not exported → graph.py can't build the state schema.
   Pipeline fails to start. Every briefing fails.


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FILE 7 — tests/test_agents.py
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   37 unit tests, zero real API calls or LLM calls. Organised into 6
   test classes:

   TestAnalystFinding (5 tests)
     → finding_id is deterministic, differs by source, to_slack_line
       formats correctly for URGENT/WATCH/zero overdue/with detail.

   TestAnalystReport (2 tests)
     → urgent_count and watch_count computed correctly, empty defaults.

   TestDecisionOutput (3 tests)
     → is_empty for all three ways it can be false.

   TestAnalystAgentRuleBased (13 tests)
     → Stale unassigned ticket → URGENT. Fresh ticket → not flagged.
       Completed ticket → not flagged. Stale PR no reviewer → URGENT.
       Fresh PR → not flagged. Draft PR → not flagged.
       Stale Notion page → WATCH. Archived page → not flagged.
       Findings sorted urgent-first. LLM failure → graceful fallback.
       JSON parsing: valid, invalid, code-fence stripping.

   TestDecisionAgent (7 tests)
     → Urgent bucket, watch bucket, dedup skips seen findings,
       dedup is per briefing_type, cap at 5, suggestion from finding,
       empty report → empty decision.

   TestActionAgentFallbackText (4 tests)
     → Empty decision text, urgent count in text, suggestion in text,
       weekly digest label.

   TestAgentState (3 tests)
     → Default briefing_type, empty run_errors, state with report.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why test every staleness edge case individually?
   → The staleness rules are the core product logic. "5 days" is a
     promise to the founder. Testing fresh/stale/draft/archived/completed
     separately makes it obvious exactly which condition broke if a test
     fails. One big test would just say "something in staleness is wrong."

   Why test dedup is per briefing_type?
   → This is a subtle requirement that could easily be broken by someone
     simplifying the dedup store to a flat set. Without this test, the
     regression would be invisible — the EOD pulse would silently stop
     showing items that appeared in the morning brief.

   Why use use_llm=False in almost all Analyst tests?
   → Tests that call Gemini need a real API key and internet. They'd
     be slow, flaky, and blocked in CI. Testing the rule-based layer
     separately means the 13 tests run in under 2 seconds.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: _ticket() fixture defaults to days_old=6 but threshold is 5
   → All staleness tests use a ticket that IS stale. If someone changes
     the default to days_old=3, all "stale ticket" tests pass even if
     the threshold is broken (3 < 5, so no finding → assert len==0 passes
     for the wrong reason).

   Bug: setup_method doesn't clear _seen_finding_ids
   → Dedup tests bleed into each other. A finding seen in one test is
     "seen" in the next. Tests fail randomly depending on run order.
     This is already correct in our code — worth knowing it must stay.

   Bug: @pytest.mark.asyncio removed from async tests
   → pytest-asyncio doesn't run them as coroutines — they pass trivially
     without executing any code. All 13 async Analyst tests show PASSED
     but nothing was actually tested.

FILE 8 — conftest.py  (bonus file added during Step 3)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. WHAT DOES THIS FILE DO?
   A pytest configuration file that runs before any test module is loaded.
   It sets all 18 required environment variables (SECRET_KEY, DATABASE_URL,
   GOOGLE_API_KEY, all integration keys...) using os.environ.setdefault().
   Then clears the settings LRU cache so the new env vars are picked up.

   This means every test file can import from app.* without needing a
   real .env file. No test needs to mock Settings or patch os.environ
   individually.

2. WHY DID WE MAKE IT THIS WAY AND NOT ANOTHER WAY?

   Why setdefault() instead of direct assignment?
   → setdefault() only sets the value if the key doesn't already exist.
   → If a developer runs tests with a real .env loaded (their dev machine),
     the real values win over the test fakes. This prevents accidental
     credential leaks while still making CI work with no .env at all.

   Why is this in conftest.py instead of a pytest fixture?
   → conftest.py at the project root runs at collection time, before any
     test module is even imported. A fixture runs after imports.
     If we used a fixture, the settings proxy would fire during the import
     of test_agents.py (before the fixture set env vars) and crash.

   Why call get_settings.cache_clear()?
   → If any other import (e.g. conftest imports an app module) already
     triggered the cache to build with missing env vars and failed, the
     cache holds the failed state. Clearing it forces a fresh load with
     the newly set env vars.

3. WHAT BREAKS IF THIS FILE HAS A BUG?

   Bug: A required settings key is missing from _TEST_ENV
   → That specific test that touches the missing key crashes with
     ValidationError. Easy to diagnose — the error names the missing key.

   Bug: cache_clear() is removed
   → On machines where the settings cache was already populated before
     conftest.py ran, the new env vars are ignored. Tests that access
     settings (e.g. stale_ticket_days) get the wrong values.

   Bug: conftest.py is moved to tests/ subdirectory instead of root
   → It no longer applies to all test files (pytest conftest.py scope is
     the directory it's in and below). Tests in tests/ still work but if
     any test file is ever added at the root level, it crashes.
